# Desktop parity checklist

The Phase 6 gate: what the Android app (Komikku) does and whether the desktop app does it. "Yes"
means the desktop app has it, with the Android data, preferences and backups, so a library moves
between the two. "Exception" rows are the proposed differences; each says why.

## Browse

| Android feature | Desktop | Notes |
|---|---|---|
| Sources, extensions, extension stores, global search | Yes | Phase 2. ## Security, sync and connections

| Android feature | Desktop | Notes |
|---|---|---|
| App lock | Yes, changed | A password kept hashed in the OS secret store, instead of biometrics or the device PIN; lock when idle, days and times as on Android. The app counts as in the background when its window is minimized or in the tray, or when another app's window becomes the active one (Android: the app is no longer on screen); "Lock when idle" counts from that moment, and "Always" locks when the app comes back. A locked computer is not detected by itself. While locked, the built-in browser windows hide and come back at the unlock, and a Cloudflare challenge met in the background waits for the unlock (within its usual 3 minutes) before its window opens; the hidden attempt runs as usual. Locking keeps the screen, its back stack and saved state, but closes open dialogs and drops text not yet saved on the screen behind it; Android keeps them under the unlock screen. If the OS secret store cannot be read while the lock is on, the app stays locked |
| Hide notification content | Yes | |
| Incognito mode and incognito extensions | Yes | No history, progress or tracking |
| Secure screen (block screenshots) | Yes, changed | Always, Incognito (the default; app-wide incognito mode) or Never, as on Android, for the main window and the built-in browser windows. Windows 10 2004 and later leave the windows out of screenshots, recordings and screen sharing (older Windows shows them black); macOS sets the windows' sharing type to none, which some newer capture tools ignore; Linux has no such setting, so nothing changes there |
| Data sync: SyncYomi and WebDAV | Yes, changed | Settings > Data sync; the Android merge, on its interval and triggers. Sync (and the command line `backup restore`) never adds an extension store or changes a store's signing key, which Android's sync does: the skipped stores are named in a notification, to add in Browse > Extensions > Stores or through a Settings restore, which asks first. A remote library that the server sends but that cannot be read (damaged, or not a backup) is a sync error and is left as it is; upstream's WebDAV and SyncYomi services treat it as no remote library and replace it with this device's library (Zoukan's shared services, so its Android build too, do not). A missing one (404) still gets the first upload |
| Data sync: Google Drive | No | Needs Komikku's Google OAuth client, which is a secret of the Android build |
| Discord Rich Presence | Yes, changed | Through the Discord app on the computer, so no Discord login is needed; the same options |
| System proxy | Yes, changed | Android's OkHttp follows the system or Wi-Fi proxy; the desktop follows the proxy set in the OS (`java.net.useSystemProxies`), and the built-in browser follows it by itself. Neither app has a proxy setting of its own. The desktop cannot use a proxy that asks for a password, and a PAC or WPAD setup works only as far as the JDK reads it |
| HTTP cache | Yes, changed | Android's clients keep a 5 MiB disk cache (`network_cache`), and its requests accept a cached response up to ten minutes old; the desktop's clients share a 5 MiB cache held only in memory, so it works the same within a run but starts empty at each start: one on disk would hold request addresses (search queries) and responses in plain text outside an app sandbox. The folder earlier versions left is deleted |
| Cover and image caches, custom covers | Yes, changed | Source covers, custom covers and the cache of images fetched by address are encrypted with the app's file key, so the files are not byte-compatible with Android's cover files (custom covers are in neither app's backups). Without the key nothing is cached on disk, and while incognito is on no new source cover or fetched image is cached on disk (Android caches them in incognito too). Images fetched by address send the app's cookies but keep none their responses set; Android's image loader keeps them |
| WebView: extensions' hidden WebViews | Yes, changed | They run on the built-in Chromium and report its desktop user agent for this OS, with matching client hints; on Android they use the device's WebView user agent. `http.agent` is the same user agent. Extensions read Komikku's version from the package manager, as on Android. A script's pop-up loads in place only when the extension let scripts open windows, as Android's WebView with multiple windows off, and never opens a window. Downloads are cancelled. The top frame goes only to http, https, `about:blank` or the address the extension asked for (Android's WebView also opens `file:` and other schemes it knows). A page's alert, confirm and prompt reach the extension's `WebChromeClient` as on Android, except from a frame of another origin or past 3 in 10 seconds (suppressed, where Android delivers them); one the client does not handle is cancelled, and so is one it keeps but has not answered after 60 seconds (Android waits for the client indefinitely), and `onbeforeunload` is always answered "leave" without asking the client. A page with no web origin (`about:blank`, or `loadDataWithBaseURL` with no base address) gets its own dialogs under the same limit, as on Android; on an http or https page a dialog with no web origin is still suppressed. A `history.pushState` to another address lifts a page's silence. For a top-frame navigation it cancels, `shouldOverrideUrlLoading` is posted to the WebView's looper and its answer ignored: Android calls it before the navigation and lets its answer decide; here the navigation is cancelled either way |
| WebView: built-in browser privacy | Yes, changed | The desktop saves no browser history and deletes history, caches and Chromium's log at start and at quit; the HTTP cache is near zero, so pages load more slowly. Spellcheck, password saving and autofill are off, WebRTC uses no non-proxied UDP, and Chromium writes no log unless debugging. A pop-up to the same site loads in the window; one to another site is offered in a "Pop-up blocked" bar (dropped in Cloudflare checks); no native window opens. A file download is cancelled, where Android hands it to the system |
| WebView: third-party cookies | Exception | Allowed in the built-in browser and extensions' WebViews; Android's WebView blocks them by default. A maintainer decision, recorded as an accepted risk in `desktop/THREAT-MODEL.md`; the content blocker removes the known ad and tracker hosts |
